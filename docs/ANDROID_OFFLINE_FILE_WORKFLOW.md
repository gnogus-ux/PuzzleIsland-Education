# 오프라인 Android 편집 파일을 PC MAY로 가져오기

2026-11-09 제작 전 적용 매뉴얼·명세 초안. 공식 Android 자료 4개와 기존 공용 목록을 확인했다. 앱·APK 빌드·파일 왕복 실기·PC 가져오기 성공을 주장하지 않는다. 기존 사진·사용자 초안·PC 저장본을 보존하며, Cloudflare·VPN·이메일 인증·외부 PC 접속은 사용하지 않는다.

## 최소 작업 흐름

1. **PC MAY에서 휴대폰 작업 파일 내보내기**: 사용자가 선택한 제품/부품/사진과 편집 기준 상태를 묶는다. 새 시험 데이터나 다른 지갑의 동명 부품을 원본 대신 넣지 않는다.
2. **폰 앱에서 작업 파일 열기**: Android 시스템 파일 선택기로 사용자가 고른 파일만 읽는다. 선택한 사진·기준선·점·가이드의 편집 UI는 검수된 MAY 화면과 동작을 재사용한다.
3. **폰에서 오프라인 편집·기기 내 초안 저장**: 사진 원본 픽셀 좌표와 ID를 유지한다. 앱을 닫거나 화면을 회전한 뒤에도 초안을 복구한다. PC가 꺼져 있거나 네트워크가 없어도 편집을 계속할 수 있어야 한다.
4. **PC로 보낼 수정 파일 저장**: 폰 앱의 별도 내보내기 버튼으로 새 파일을 생성한다. 사용자 선택 위치에 파일이 기록됐는지 확인한다. 초안 저장·파일 내보내기·PC 반영을 각각 표시한다.
5. **사용자가 파일을 PC로 전달**: 예를 들어 USB 파일 복사 등 사용자가 고른 방법으로 옮긴다. 이 기능이 파일을 자동으로 PC에 동기화하거나 전송 완료를 자동 보증한다고 하지 않는다.
6. **PC MAY에서 수정 파일 선택 → 검사·차이 보기 → 가져오기**: 사진/부품/기준 버전과 충돌을 확인한 뒤 사용자가 명시적으로 반영한다. 반영 뒤 새 revision과 가져오기 기록을 저장하고 실제 계산을 다시 수행한다.

## 1. 기존 편집기를 오프라인으로 재사용하는 경계

사진 표시·확대/이동·점 선택/이동·기준선/가이드 표시·미세 조절·실행 취소 등 검수된 프런트엔드 동작을 가져온다. 기존 UI가 호출하던 PC API는 폰 앱의 로컬 상태 계층으로 교체해야 한다. HTML을 WebView로 감싼 것만으로 서버 의존 기능이 오프라인이 됐다고 말하지 않는다.

PC의 Python 계산·Blender 작업·AI 분석을 폰에서 실행한다고 가정하지 않는다. 첫 범위는 사진·점·선·분류·설명의 편집과 교환이다. 폰에서 서버 계산을 재현하지 못한 수치는 보류/미리보기로 구분하고 PC 가져오기 후 원래 계산기로 재평가한다. 물리 두께·숨은 층·제조 정확도나 사용자의 최종 승인을 파일만으로 확정하지 않는다.

## 2. 안전한 로컬 WebView 구성

[공식 로컬 콘텐츠 문서](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content)는 앱에 포함한 HTML/JS/CSS가 네트워크 없이 동작할 수 있음을 설명한다. WebViewAssetLoader는 HTTP(S) 형태의 로컬 origin과 하위 리소스 처리를 제공한다. **AndroidX WebKit 의존성이 기존 환경에 있는지는 아직 미확인**이므로 자동 다운로드하지 않는다.

하위 리소스 가로채기가 필요 없는 단일 HTML 구성은 프레임워크의 `loadDataWithBaseURL()`을 검토할 수 있다. 이 경우 실제 외부 서버 주소가 아닌 앱 전용 합성 origin과 완전히 포함된 자원을 사용하고, 서버 API fetch가 남지 않도록 오프라인 어댑터를 검수한다. 필요한 로컬 사진 제공 방식을 확인하지 않은 채 단일 HTML 방식으로 모든 패키지를 처리할 수 있다고 단정하지 않는다.

`file://`·`content://` 경로를 웹페이지 주소로 직접 열거나 universal/file URL 접근을 켜서 우회하지 않는다. file/universal 접근은 명시적으로 끄고 혼합 콘텐츠를 허용하지 않는다. 외부 링크·탑레벨 탐색·외부 하위 리소스·iframe·팝업·임의 intent를 차단한다. 파일 선택기의 content URI는 네이티브 코드가 선택된 파일을 읽는 용도로만 사용한다. 공개 네트워크 기능이 없는 앱으로 설계하며 INTERNET 권한이 꼭 필요한지 검토하고, 네트워크 없이의 실행을 실제 검사한다.

[공식 네이티브 bridge 보안 문서](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)는 JavascriptInterface가 모든 frame에 노출되고 호출 origin을 확인하기 어렵다고 설명한다. 임의 HTML/JS를 파일에서 실행하거나 광범위한 파일/프로세스 접근 메서드를 bridge에 제공하지 않는다. native↔JS 전달이 필요하면 신뢰된 로컬 문서만 허용하고, 메서드·메시지 종류·크기·정확한 origin·스키마를 제한한다. 문자열을 코드로 이어 붙여 실행하지 않고 JSON으로 직렬화한다. 입력 JSON의 라벨/설명/파일명을 HTML로 해석하지 않는다. JavaScript가 필요한 편집 기능과 네이티브 파일 입출력을 구분한다.

## 3. Android 문서 파일 입출력과 초안 보존

[Storage Access Framework 공식 문서](https://developer.android.com/training/data-storage/shared/documents-files)는 `ACTION_OPEN_DOCUMENT`로 파일을 고르고 `ACTION_CREATE_DOCUMENT`로 새 파일을 저장하는 흐름을 제공한다. broad storage 권한이나 새 계정 없이 사용자 선택 문서의 URI를 사용한다. 선택기는 외부 provider도 보여 줄 수 있으므로 오프라인 시 로컬 저장 위치를 선택하고, cloud provider가 선택된 경우의 실패/대기를 로컬 성공으로 표시하지 않는다.

초안은 앱 전용 저장소에 먼저 보존한다. 파일 선택 취소·권한 회수·부족한 공간·중간 쓰기 실패·앱 종료가 있어도 편집 상태를 버리지 않는다. URI의 display name을 신뢰할 경로로 간주하지 않고 content resolver로 읽고 쓴다. 내용 크기를 모르는 URI도 실제 스트림에서 제한한다. 완전한 파일 기록을 확인한 뒤에만 내보내기 완료로 표시한다. 같은 이름 새 파일 생성과 기존 파일 교체를 구분한다. 기존 원본과 이전 내보내기 파일은 보존한다.

## 4. 파일 계약 — 제안 스키마, 실제 값 아님

초기 PC→폰 작업 패키지는 JSON manifest와 필요한 사진을 묶은 버전 있는 컨테이너를 권장한다. ZIP은 Android와 PC의 기존 표준 라이브러리를 검토할 수 있어 새 압축 프로그램을 전제하지 않는다. 폰→PC 수정 파일은 사진이 바뀌지 않았다면 같은 사진 SHA를 참조하는 편집 데이터만 포함할 수 있다. 형식명·확장자·지원 버전은 양쪽이 하나의 계약으로 정한다.

필수 필드의 역할:

| 필드 | 의미 |
|---|---|
| format/schemaVersion/editorBuild | 파일 종류·지원 스키마·편집기 호환 근거 |
| packageId/changeSetId | 가져온 작업과 수정 결과의 식별·중복 반영 방지 |
| projectId/productId/partId/photoId | 기존 PC 자료와의 정확한 대응 |
| baseRevisions/baseSnapshotSha256 | 편집 시작 당시 각 구성의 revision과 기준 상태 해시 |
| photos | 원본 SHA256·실제 표시 이미지 SHA256·해상도·orientation/좌표 기준 |
| edits | 원본 사진 픽셀 좌표·선/점/분류·단위/기준선·설명·보존 경계 |
| provenance | 기기 편집 후보·원래 근거·사용자 확인 범위·미검증 상태 |

PC에 이미 있는 ID와 사진 SHA·좌표 기준이 맞아야 연결한다. 동명 부품·비슷한 사진·휴대폰 파일명만으로 자동 연결하지 않는다. 사진 해시만 맞아도 기준 revision이 다르면 충돌일 수 있다. 파일에 기록된 SHA는 손상/일치 검사이며 작성자 인증·파일 신뢰 보증은 아니다.

## 5. PC 가져오기 검증·충돌·원본 보존

파일을 고르는 즉시 현재 프로젝트를 덮어쓰지 않는다. 임시 후보로 읽고 다음을 검사한다.

- 허용 형식/스키마·필수 필드·타입·유한 수치·문자열/배열 크기·좌표 범위·사진 해상도를 검사한다. 미지원 버전·임의 필드/작업·실행 코드는 거부한다.
- 사진 바이트의 SHA와 선언값을 직접 대조한다. 부품·사진 ID/방향/단위가 기존 PC 자료와 맞는지 확인한다. 폰의 경로·URI를 PC 경로로 실행/열지 않는다.
- [공식 ZIP 경로 순회 문서](https://developer.android.com/privacy-and-security/risks/zip-path-traversal)는 기본 zip 라이브러리가 안전한 추출을 대신하지 않는다고 설명한다. 임의 엔트리 경로를 추출하지 않고 정해진 멤버를 바이트 스트림으로 읽어 앱이 정한 이름으로 처리하는 방식을 우선한다. 절대/부모 경로·중복 이름·허용 외 멤버를 거부한다. 경로 추출이 필요하면 symlink까지 판별 가능한 도구인지 확인하고 안전한 임시 영역 밖 쓰기를 막는다. 멤버 수·압축/해제 실제 바이트·사진 디코딩 크기를 제한한다. 중앙 디렉터리의 선언 크기만 믿지 않는다.
- 현재 PC의 base revision과 기준 스냅샷이 다르면 자동 덮어쓰지 않고 차이/충돌을 보여 준다. 사용자는 취소·새 후보로 보존·검토 후 적용을 선택할 수 있어야 한다.
- 미리보기 결과와 최종 반영 사이에도 revision을 다시 확인한다. 최종 반영은 검증·보존 후 새 revision 하나로 저장하며 실패 시 기존 자료가 남아야 한다. 같은 changeSetId를 다시 가져오면 중복 반영을 막는다.
- 점/기준선/사진/분류가 바뀐 결과의 기존 계산·확인을 자동 승계하지 않는다. 변경된 범위의 확인을 해제하고 PC에서 재계산한다. 가져오기 후보·사용자 적용·최종 제품 승인을 구분한다.

포맷의 크기/장수/개수 제한은 기존 MAY의 프로젝트·사진 제한과 실제 기기 메모리를 확인해 정한다. 시험 예제를 전체 제품의 보편 제한으로 하드코딩하지 않는다. 파일 미리보기에는 변경 대상·좌표/선 차이·충돌·실제 반영 범위를 보여 주고 구현 세부를 사용자 판단에 불필요하게 노출하지 않는다.

## 제작·검수의 최소 완료 조건

기존 SDK/JDK/빌드 도구·플러그인/캐시·지원 Android API를 먼저 확인한다. WebViewAssetLoader나 새 빌드 의존성이 없으면 무단 설치/다운로드하지 않고 기존 프레임워크로 가능한 경로와 부족한 정확한 항목을 보고한다. APK 생성, 서명 확인, 사용자 허용 설치, 실제 기기 오프라인 실행은 각각 별도 검증이다. 신규 설치 권한 창·기기 보안·계정 인증은 대신 처리하지 않는다.

실기 순서는 PC 기준 파일 생성→폰 파일 열기→네트워크 없는 상태의 실제 편집·초안 복구→SAF 새 파일 저장→PC 실제 파일 선택→차이 미리보기→명시 적용→PC 재열기에서 좌표/사진 SHA·새 revision 확인이다. 외부 resource 요청 0과 잘못된 package/SHA/revision·중복/손상/경로순회 파일 거부, 취소/저장 실패 시 기존 초안·PC 원본 보존도 확인한다. 측정/가이드 UI를 재사용하더라도 기존 계산·확인 무효화 회귀를 별도로 검수한다.

이 흐름은 **파일을 매개로 한 수동 전달과 명시 가져오기**다. 실시간 원격제어·자동 PC 동기화·Cloudflare 재사용을 추가하지 않는다. 공용 게시에는 실제 사진·개인 경로·serial·이메일·외부 주소를 포함하지 않는다.
