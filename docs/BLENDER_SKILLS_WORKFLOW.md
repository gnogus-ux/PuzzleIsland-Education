# 외부 Blender 스킬을 제작 절차로 읽는 법

2026-11-01 · 문서 학습 매뉴얼 · 실제 모델 수정·실기 검증 없음

EL4CTEO Blender 28개와 Scenario Blender 15개 SKILL 본문을 전체 확인했다. 각 파일의 고정 커밋 출처·한 줄 요점·읽은 범위는 [Blender 색인](BLENDER_SKILLS_INDEX.md), 정확한 바이트 해시는 검증 JSON에 있다. 원문이 제시한 시험 성적은 저자의 보고다. 이번 학습에서 그 시험·스크립트·Blender를 실행하지 않았다. 참고 영상은 재생하지 않았다.

## 시작 조건과 작업 계약

승인 이미지와 최신 파일, 보존할 오브젝트·UV·이미지·키·가중치·리그를 먼저 고정한다. 모델 수치가 강좌의 성인 비례와 다르다는 이유로 승인된 어린이 캐릭터를 변경하지 않는다. 별도 머리와 제작 중 베이스 등 기존 자산도 프로젝트의 보존 경계다. 이 교육은 눈·입 수정이나 리깅 재개 지시가 아니다.

변경 작업이 승인되었을 때에는 현재 live 상태의 checkpoint → 별도 Guide의 수정 범위·목표 윤곽·이동 방향·보존선·접속 경계 → Guide 저장과 점유 해제 → 담당 단독 점유 → 별도 후보 → 같은 solid/wire 조건의 전후 검수 순서로 진행한다. 외부 스킬의 자동 원본 삭제·일괄 purge·기본 장면 초기화 예제는 사용자 파일에서 실행할 절차가 아니다.

작업 계약에는 단위와 실제 크기, 피벗, 목적(게임/영상/정지화면), 카메라 거리, 폴리곤·뼈·텍스처 예산, 채널 규약, 허용한 자동 수정, 파일 경로를 기록한다. 원문의 2K, 3루프, 2026 예산표를 미정 사양의 대용으로 사용하지 않는다.

## 장면·코드·반복 작업

EL core/scene-setup/addon-development/pipeline-automation, Scenario expert가 공통 기반이다. 기존 데이터에는 최소 읽기부터 접근하고, 편집 대상과 모드·선택·평가 상태를 확인한다. 데이터 API가 가능한 작업은 문맥 의존 연산자보다 우선한다. 연산자는 반환값과 poll을 확인하고 필요한 문맥만 지정한다. Object 모드 mesh와 Edit 모드 BMesh를 혼용하지 않으며, 평가 메시를 읽었으면 해제한다.

이름을 요청한 결과가 같은 이름이라는 보장은 없다. 생성 반환값을 사용하고, 반복 작업에는 소유 태그·별도 컬렉션·재실행 시 중복 여부를 둔다. 모드 전환·삭제·배열 재할당 뒤에는 필요한 참조를 새로 읽는다. BMesh 인덱스는 위상 편집 전후로 동일한 의미라고 가정하지 않는다. 면 코너의 UV를 정점 속성처럼 덮어쓰지 않는다.

백그라운드 시험은 사용자 장면과 분리한 사본에서만 가능하다. factory-startup·종료코드·로그·절대 경로·저장 후 재열기 검사는 별도 실기 계획이며 이번에는 실행하지 않았다. 애드온 등록·해제나 외부 브리지 설정도 교육 때문에 설치하지 않는다. Scenario의 `execute_python`과 EL의 MCP 도구 이름은 현재 연결의 실제 도구 계약을 대신하지 않는다.

원문은 Blender 5.2/5.2.1 및 5.x의 Principled 소켓, action slot/channelbag, GN 입력, 합성 노드, 이미지 형식 API 변경을 설명한다. 이 명칭은 고정 스냅샷의 주장이다. 실제 편집 전에 현재 Blender 버전과 구조화 도구 스키마/RNA를 확인해야 하며 이번 학습에서 로컬 동작을 확인한 것은 아니다.

## 모델링·스컬프·리토폴로지

EL hardsurface-modeling/sculpting/retopology-uv와 Scenario hard-surface/sculpting/retopology를 함께 읽는다. 큰 형태 → 기능 분리 → 보조 형태 → 디테일 순서다. 형태를 규정하는 가장 좁은 홈·곡면·실루엣에 필요한 면을 확보하고, 지지 루프·bevel·crease·normal bake 중 목적에 맞는 방법을 선택한다. modifier 순서는 고정 공식이 아니다. 평면 boolean용 n-gon과 변형하는 얼굴 cage를 같은 기준으로 판정하지 않는다.

스컬프의 Voxel/Dyntopo/자동 remesh는 UV·정점 그룹·키·세부 형태를 잃을 수 있다. 먼저 사본·저해상도 큰 형태를 쓰고, 확정된 형태 뒤에 세부를 올린다. Quadriflow나 Decimate는 애니메이션용 흐름·원본 UV·실루엣 보존을 보장하지 않는다. 자동 원본 정리와 얼굴 수선은 별개다.

Scenario의 여섯 지도 층은 흐름, 주/보조 주름, 관절, 표정 범위, 랜드마크를 메시보다 먼저 데이터로 설계한다는 점이 유용하다. 프로젝트에서는 이를 현재 표면의 실제 Guide에 연결한다. 눈과 입의 독립 루프, 코·볼·이마 전환, 관절 단면, 접속 경계의 순서·수·방향을 먼저 정한다. 경계 수를 맞추기 위해 눈꼬리를 압축하거나 고정 18/24점에 억지로 맞추지 않는다.

먼저 개별 패치를 만들고 순서가 맞는 경계를 연결한 뒤 국소 용접한다. 오브젝트 Join, 패치 내부 연결, 중앙 seam, 사용자 원본 피부와의 접속을 각각 판정한다. 가까운 3D 점이 다른 표면(입술·귀·손가락)일 수 있으므로 최근접 투영만으로 대응을 결정하지 않는다.

검수는 원 cage와 Subdivision 평가 표면 모두에서 한다. 정점뿐 아니라 엣지·면 중앙의 이격, 폴의 위치, 관통과 열린 경계, 사선의 볼륨을 확인한다. Scenario의 양 예제는 평균 이격이 더 작은 자동 fit이 오히려 울퉁불퉁하게 보였다고 보고한다. 폴 비율·quad 비율·inside 비율 하나로 PASS를 만들지 않는다. 원문 안에서도 inside 40–60% 목표와 55% 초과 수축 경고가 겹쳐, 모델별 보정 없이 합격선으로 쓸 수 없다.

## UV·텍스처·베이크

EL texturing/retopology-uv/texture-baking/PBR, Scenario uv-baking/texturing-shading 순서다. 기존 UV/이미지가 있으면 전체 재전개 전에 대응과 영향 범위를 보존한다. 고유 페인팅, 반복 재질, 의도한 겹침, UDIM 지원, 최종 카메라와 최소 mip를 먼저 정한다. 면 방향과 숨은 절개 위치를 고려해 시임 → 후보 unwrap → 왜곡·접힘 → 밀도 → 패킹 → 실제 이미지 검사로 진행한다.

`BEST`는 Scenario 래퍼가 섬별 후보를 비교하는 방식이며 Blender 연산자의 보편적인 enum이 아니다. unwrap이 FINISHED를 반환해도 실패 섬에 이전 UV가 남을 수 있다는 저자 사례가 있으므로 결과 좌표·체커를 검사한다. 진단용 초기화 예제를 이미 칠한 사용자 UV에 적용하지 않는다.

밀도는 px/m 또는 px/cm 단위와 이미지 크기를 함께 기록한다. 얼굴의 추가 배정은 카메라·승인 디테일에 이유를 둔다. 고정 same density나 hero 2배를 법칙으로 만들지 않는다. 패킹 중 자동 확대가 밀도를 바꾸는지 재측정한다. 섬 사이 간격과 타일 경계 여백을 구분하고 mip·필터·압축에서 확인한다. 원문 FRACTION 계산은 해당 버전의 저자 실측이며 로컬 재현 전 확정하지 않는다.

베이크는 동일한 삼각화·tangent basis, low UV, high/low 쌍, 활성 이미지 노드와 슬롯, 거리/케이지, 채널, 저장 경로를 명시한다. 가까운 부품의 잘못된 투영은 거리만 계속 키우지 말고 쌍별 분리·케이지·형태 수선으로 진단한다. Scenario의 자동 cage는 양 예제에서 더 나빴다고 명시한 실험 기능이다. adaptive 투영의 개선 비율·실행시간도 그 예제의 보고다.

원문 mirror +1U 방식은 0–1 반복 셰이더와 해당 baker의 타일 처리 조건에서만 검토한다. UDIM이나 비대칭 AO·문양에 보편적으로 적용하지 않는다. 평평한 tangent normal이나 흰 AO 영역은 의도된 표면일 수 있다. 이미지 통계만으로 실패라 단정하지 말고 문제 픽셀을 모델에 표시해 원인을 찾는다. 베이크 파일을 실제 저장·재열기하고 재질에서 확인해야 완료다.

색 이미지는 색공간을, normal/roughness/metal/AO는 데이터 규약을 따른다. ORM과 Unity Metallic/Smoothness·HDRP Mask는 다르다. 노멀 OpenGL/DirectX와 녹색 채널, displacement의 중립값·스케일도 기록한다. 같은 요철을 이중으로 넣는 실수는 피하되 macro displacement와 micro normal의 병용까지 금지하지 않는다. 승인된 양식에 없는 거칠기 노이즈나 피부 투과를 무조건 추가하지 않는다.

## 옷·머리·리그·애니메이션

EL clothing/hair-grooming/character-rigging/facial-shapekeys/animation, Scenario hair/rigging/animation이 연결된다. 의상은 몸 복사·여유·두께·몸 가림 정책을 별도로 설계하고 원본 몸을 삭제하지 않는다. 가중치와 키 복사 후 실제 포즈 검사는 승인된 단계에서 한다. 머리는 흐름·가르마·적은 가이드 → clump → 분포·길이 변화 → full-count 렌더·관통 검수로 간다. 브러시 활성화 성공과 stroke가 실제 곡선을 바꾸는 것은 다르다. 모바일에는 카드·투명 겹침 비용까지 별도 검증한다.

리그는 생성 완료보다 실제 관절 배치·roll·가중치 분포·변형이 기준이다. 자동 heat가 FINISHED여도 비어 있는 주요 그룹이나 잘못된 전이가 있을 수 있다. controls와 export 변형 골격을 분리하고, 필요한 범위의 관절·twist·영향 수를 사양으로 고정한다. 원문의 성인 높이, 뼈 수, 4영향, 50:50 비율을 루미 사양으로 정하지 않는다.

표정 키는 이름 목록만으로 완성되지 않는다. ARKit52, Meta15 viseme, Roblox joint pose는 서로 다른 계약이다. `sil`처럼 의도된 중립 키는 비어 있을 수 있고 사용하지 않는 키는 제거 대상일 수 있다. 모든 키의 이동·0–1 clamp·relative만 export 가능이라는 절대 설명은 엔진/포맷/버전별로 제한해야 한다. 원본 키의 정점 순서를 보존하고, 승인된 후속 단계에서 극값·조합·눈꺼풀 접촉을 검수한다. 특수 안구 구조나 광학을 이 자료로 실증했다고 주장하지 않는다.

애니메이션은 의도·접지·저항·타이밍을 큰 포즈에 먼저 담고, 몸 → 얼굴·손 → overlap → polish로 간다. spline으로 바꾸어 흐려지면 breakdown을 보강한다. 화면 공간 궤적과 실제 재생을 곡선 통계와 함께 본다. 원문의 24fps·2프레임 시선 이동·탄도 오차는 특정 스타일의 시작값이다. 움직임 보류를 해제하지 않는다.

## 환경·렌더·영상과 특수 주제

EL environment-kits/geometry-nodes/game-optimization은 모듈 단위·피벗·접합 규격, instance 유지, 실루엣별 LOD, UV/normal/material로 분할되는 실제 엔진 정점 비용을 다룬다. Join은 culling을 악화시킬 수 있고 같은 재질이 자동으로 1 draw call이 되는 것은 아니다. 숨은 면 삭제는 다른 의상·시점의 노출을 먼저 확인한다. GN은 유효한 링크와 평가 결과를 검사하며 정점 생성 숫자만으로 시각 품질을 판정하지 않는다.

EL lighting-lookdev/rendering/stylized-npr/time-of-day/weather-fx/simulation은 회색 재질·고정 카메라에서 형태를 먼저 읽고, 최종 광원·색관리·출력 조건에서 확인하는 자료다. toon Shader to RGB, custom normal, SDF 얼굴 음영은 렌더러·스타일별 기술이며 모바일 성능이나 안구 구조를 입증하지 않는다. 시간·날씨는 광원/하늘/안개/젖음의 연속성을, 시뮬레이션은 단위/캐시/범위/충돌을 따로 검수한다. 조명 전력 예제·fill 비율을 물리 법칙이나 승인 스타일로 고정하지 않는다.

Scenario grease-pencil은 점·stroke 대응, fill·구멍·깊이, 2.5D cutout과 변형 방식의 선택을 다룬다. Line Art 두께와 radius, World와 unlit layer 같은 버전 차이를 확인한다. EL video-editing과 Scenario previs-storyboard는 별도 편집 scene, FPS·음원·카메라 marker·cut 경계·실제 인코딩 프레임을 확인한다. Scenario blockout의 영상 생성 가이드, 감독용 previs, 게임 레벨 블록아웃은 목적이 다르다. 영상 모델이 가이드의 동작·정체성을 반드시 지킨다고 보장하지 않는다. EL workflow-recipes는 이런 단계를 묶는 시작점이며 누락된 시각 검수를 대체하지 않는다.

## 실패 때 돌아갈 단계와 인계

| 증상 | 먼저 확인 | 인계에 남길 것 |
|---|---|---|
| 수치는 좋지만 얼굴이 울퉁불퉁함 | 목표 윤곽·폴·국소 간격·면 중앙·평가 스택 | 동일 solid/wire, Guide 대비 미달 위치 |
| 베이크 거리 변경에도 같은 반전 | high/low 형태 차이·얇은 부위·다른 부품 투영 | 문제 픽셀의 모델 위치, 쌍·거리·케이지 |
| 키 이름은 있으나 움직이지 않음 | 중립/미사용 구분, 실제 delta·driver·export | 요청된 키만의 변형 보고, 미검증 항목 |
| 내보낸 축·scale이 틀림 | 실제 파일·importer·root 변환·프리셋 | 설정·재임포트 비교와 알려진 차이 |
| 호출 timeout | 실제 적용·저장·점유 상태 | 마지막 확인된 변경과 재실행 여부 |

저장 파일, 원본 대비 보존 기록, 수치 검사, 실제 본 시각 근거, 완료/부분/미검증, 다음 담당이 해야 할 범위를 함께 넘긴다. EL QA의 큰 메시에서 생략한 z-fighting/떠 있는 면 검사는 PASS가 아니라 생략이다. 문서 게시나 저장 성공은 루미 시각 개선의 성공이 아니다.
