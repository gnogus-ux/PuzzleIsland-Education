## 1. 필요한 문서를 고르는 법

먼저 실제 프로젝트의 엔진·고정 버전·패키지 잠금·입력·렌더러·기존 담당 시스템을 확인한다. 엔진 하나를 정하고 해당 엔진의 구현 문서에 공통 개념과 장르 문서를 더한다. 서로 다른 엔진의 비슷한 클래스명을 혼합하지 않는다. 예를 들어 Unity 퍼즐은 C# 수명·입력·SO 문서에 puzzle/save/UI를 더하고 기존 Match3 규칙을 우선한다.

| 작업 질문 | 읽을 조합 | 남길 산출물 |
|---|---|---|
| 보드가 연타 때 깨지는가 | puzzle + input + 엔진 수명 + 기존 Match3 | 수락 명령·해결 소유자·상태 전이·최소판 |
| NPC가 방향을 계속 바꾸는가 | game-ai + BT/Utility + 엔진 내비게이션 | 결정 점수·분기·취소·경로 실패 기록 |
| 화면에 따라 조작이 어긋나는가 | camera + input + UI + 엔진 좌표 | 화면→로컬→논리 좌표 계약·포커스 흐름 |
| 저장이 가끔 이전 상태가 되는가 | save-systems + 엔진/서버 저장 | schema·revision·충돌·복구·고유 거래 계약 |
| 느린 장면을 줄이려는가 | performance + 관련 렌더/물리 | 동일 장면·대상 기기·병목·변경 전후 측정 |
| 모듈을 엔진으로 옮기는가 | level-design + 엔진 가져오기 + 기존 모듈러 | 접합·충돌·경로·카메라·재수출 인계 |

router의 새 프로젝트 기본값은 기존 프로젝트를 다른 엔진으로 바꾸라는 지시가 아니다. 스킬에 있는 설치·로그인·플러그인 활성화·앱 연결·업로드 절차도 교육 내용이며 현재 승인 범위를 확장하지 않는다. 프로그램 설치·설정 보류와 금지 앱 조회 제한을 유지한다.

## 3. Unity 8개 주제의 실무 절차

### 3.1 C# 수명과 비동기 작업

Awake에서 자신의 참조를 준비하고 OnEnable에서 소유한 구독을 연결하며 OnDisable/OnDestroy에서 대응 해제한다. 서로 다른 객체의 초기화 순서를 임의로 가정하지 않는다. Start 이전 데이터 주입, inactive 상태, 씬 교체·재입장, domain reload를 끈 플레이 전환도 검수한다.

coroutine은 별도 스레드나 자동 잠금이 아니다. 기다린 뒤에는 객체·세션·요청 세대가 아직 유효한지 확인한다. async 작업에도 취소·실패·늦은 완료의 처리자를 정한다. 풀로 돌려보낸 객체를 이전 작업이 다시 변경하지 않도록 한다. 단순 hide/set_process 같은 예시는 collider·타이머·구독·오디오까지 초기화한 풀 계약이 아니다.

### 3.2 Input System

입력 장치의 키를 게임 행동으로 추상화하고 게임플레이/메뉴 Action Map의 활성 소유자를 정한다. 구독 해제와 Enable/Disable의 책임이 겹치면 중복 호출이나 다른 화면 입력 정지가 생긴다. performed가 한 번 눌림인지 지속 상태인지는 Action/Interaction 설정에 달려 있다.

누름 순간·유지·해제·취소를 구분한다. 짧은 누름은 이벤트 또는 래치로 받고 고정 스텝에서 한 번 소비한다. 재매핑에는 충돌·취소·복합 바인딩·장치별 저장·기본값 복원을 포함한다. 메뉴가 떠 있을 때 월드 입력을 막고 UI 입력 모듈과 게임 입력의 중복을 확인한다. 포인터 ID·UI 시작·화면 밖 release·초점 상실도 입력 계약이다.

### 3.3 Physics

3D Rigidbody/Collider와 2D Rigidbody2D/Collider2D를 분리한다. 물리 이동의 소유자가 Rigidbody인지 CharacterController인지 NavMeshAgent인지 정한다. 동적 바디를 Transform과 동시에 움직이지 않는다. 고정 스텝, 보간, 힘/속도/충격량의 단위와 질의 레이어·트리거 정책을 명시한다.

고속 물체의 터널링은 실제 형상·속도·스텝에서 확인한다. CCD를 켰다는 이유만으로 모든 형상과 접촉이 해결됐다고 하지 않는다. 겹침 질의는 결과 중복·버퍼 포화·자기 자신·의도하지 않은 트리거를 검수한다. 공통 물리 문서의 마스크 설명을 다른 엔진에 그대로 일반화하지 않는다.

### 3.4 Animation

Animator 파라미터와 전이 조건·레이어·Blend Tree로 상태를 제어하고 이동/애니메이션 중 누가 위치를 결정하는지 정한다. 직접 CrossFade가 항상 금지되는 것은 아니며 프로젝트가 정한 예외로 관리한다. Humanoid IK는 해당 레이어/리그 조건을 확인한다.

클립 길이만 기다리는 방식은 speed·전이·블렌드·중단을 반영하지 못한다. 시작 요청 ID와 종료/취소 결과를 연결하고 ‘다른 클립의 완료’를 오인하지 않는다. 보드 판정·피해·보상을 애니메이션 콜백에서 다시 계산하지 않는다.

### 3.5 ScriptableObject

SO는 공유 정의·설정과 런타임 세션 상태를 나누는 도구다. 원본 레벨 SO에 현재 목표 수집량·플레이어 HP를 쓰거나 Editor Play 변경을 사용자 저장으로 간주하지 않는다. 안정된 콘텐츠 ID로 저장 DTO를 연결하고 mutable 컬렉션의 복사 깊이를 명시한다.

이벤트 채널은 구독 수명·발송 순서·재진입 정책을 가진다. 원문 역순 List 순회는 자기 해제를 돕지만 다른 리스너 제거·중첩 발송까지 안전하다는 보장은 없다. 그 경우 스냅샷/지연 변경/재진입 금지 등 명시 정책을 검토한다. 이번에는 코드를 구현하지 않았다.

### 3.6 Tilemap 2D

Grid/Tilemap/Palette와 실제 보드 규칙을 분리한다. 셀 좌표와 월드/화면 좌표를 구분하고 카메라·부모 변환·원점·셀 중심을 고정한다. Rule Tile·Collider·Composite·정렬·chunk 경계를 검수한다. 타일이 보인다는 사실이 셀 통행·판정·저장 상태의 성공은 아니다.

### 3.7 NavMesh

에이전트 크기·경사·단차·Surface 수집 레이어·실제 바닥과 bake 결과를 맞춘다. 목표의 NavMesh 포함, 경로 계산 중/성공/부분/실패, 문·링크·동적 장애물 정책을 나눈다. 목적지가 같아도 매 프레임 재요청할 필요가 있는지 판단한다.

원문 HasArrived 예제의 pathPending/remainingDistance만으로 도착을 확정하지 않는다. isOnNavMesh·hasPath·pathStatus와 요청 결과를 함께 보아 경로가 없거나 실패한 경우를 구분한다. 기존 격자 이동을 NavMesh로 바꾸는 것은 별도 제작 결정이다.

### 3.8 Build Pipeline

실제 대상 플랫폼·씬/프로필·품질·URP·stripping·Addressables의 버전을 고정한다. 코드 컴파일, 에셋 수집/콘텐츠 빌드, Player 빌드, 설치·실행을 나눈다. 스트리핑 뒤 리플렉션·직렬화·동적 참조가 유지되는지 확인한다. Development는 계측용, 배포 후보는 실제 설정으로 다시 확인한다.

깨끗한 경로에서 시작·레벨 전환·저장·누락 에셋·중단 복귀를 시험해야 한다. 빌드 성공 로그는 Android 터치·Safe Area·IL2CPP·발열·성능의 성공을 대신하지 않는다. 이번 학습에서 빌드·패키지 설치·앱 실행은 전부 NOT_RUN이다.

## 4. 퍼즐·저장·레벨 설계

### 4.1 보드 해결의 책임

논리 보드가 조각·빈칸·구멍·장애물·목표 상태를 소유하고 표현은 결과를 재생한다. 입력을 한 명령으로 받아 합법성 검사→시험 교환→무효 원복 또는 수락→검출→효과 계획→제거/피해→구간 압축/보충→재검사→안정판 종료 판정→표현 완료로 진행한다. 해결 소유자는 하나다.

같은 합법성으로 실제 교환·힌트·교착을 검사한다. 빈칸을 명시 sentinel로 표현해 유효 종류 0과 혼동하지 않는다. 검사 자체가 PRNG·ID·이동 수를 소비하지 않도록 한다. next move가 하나 있다는 것은 제한된 수 안에 목표를 달성할 수 있다는 증명이 아니다.

직선 run과 flood fill은 다른 규칙이다. T/L·길이4/5의 특수 생성에는 고유 셀 집합 외에 그룹·방향·교환 원인·보존 위치가 필요하다. 원문 단순 열 압축은 직사각형의 연속 열만 다루므로 구멍/고체 장애물로 나뉜 중력 구간을 별도로 설계한다. Undo에는 조각만 아니라 PRNG 현재 상태·특수·목표·카운터도 필요하지만, Undo나 지수 배점 자체는 신규 기능 승인사항이 아니다.

### 4.2 저장·마이그레이션·복구

저장 스키마, 콘텐츠 ID, 규칙/생성기 버전, revision과 저장 시점을 정한다. seed만으로 중간 난수 상태나 다른 PRNG 버전까지 재현할 수 없다. 공유 정의/SO/씬 객체 대신 검증 가능한 순수 데이터를 저장한다. 보상은 고유 거래 ID로 중복을 막는다.

로드는 문법→schema 지원→필수 필드/범위→콘텐츠 ID→마이그레이션→런타임 적용 순서로 진행한다. 미지원 미래 버전이나 손상 데이터를 읽자마자 기존 파일에 덮어쓰지 않는다. 백업·복구·복구 불가의 경로를 정한다. 임시 파일→교체 전략도 플랫폼의 rename/원자성·동일 볼륨·실패 창·내구성 조건을 검토해야 한다. 종료 콜백만으로 저장을 보장하지 않는다.

최소 검수는 최초 저장, 과거 버전, 미래 버전, 중간 파일 손상, 쓰기 실패, 저장 중 종료, 중복 클리어, 재시작 후 동일 상태다. Roblox는 로드 성공 전 저장 금지·재시도 callback의 순수성·세션 충돌·종료 예산을 추가한다. UpdateAsync라는 이름만으로 오래된 세션 덮어쓰기가 막히지 않는다.

### 4.3 레벨과 절차 생성

행동 동사·목표·제약을 한 문장으로 정하고 블록아웃에서 거리·시야·분기·보상·휴식의 흐름을 확인한다. 이동/점프의 수학적 도달 가능성만으로 조작 성공을 확정하지 않는다. 실제 배우의 충돌 폭·회전·경사와 카메라를 사용해 검수한다.

절차 생성은 실패 seed·시도 상한·연결성·목표 접근·생성 순서를 기록한다. 같은 seed라도 라이브러리/생성기 버전·호출 순서가 바뀌면 결과가 달라질 수 있다. 문/열쇠를 단순 도달 집합으로 검사하는 모델은 비소모 열쇠와 단조로운 해금 가정이 있다. 열쇠 소비·재잠금·제한 자원·진행 목표까지 보장하지 않는다.

## 5. AI·카메라·입력·UI·성능을 연결한다

### AI의 결정과 실행

FSM은 적은 모드, BT는 조합·우선순위·중단, Utility는 연속적인 욕구 비교에 적합한 선택지다. 의도 선택, 길 찾기, 실제 조향/충돌을 분리한다. 선택한 목표에 길이 없을 때의 fallback과 센서 갱신 간격도 정책이다.

BT는 Success/Failure/Running과 시작·중단·완료 후 재진입 계약을 함께 가진다. memory Sequence는 진행 중 앞 조건을 재검사하지 않으며 상위 ReactiveSelector만 바꿔도 이 문제가 사라지지 않는다. 중단 시 이동 예약·애니메이션·타이머를 정리한다. cooldown은 분기 이탈 때 초기화하면 재진입 공격 남용이 생길 수 있다.

보충 core의 ‘complete/allocation-conscious’라는 설명에는 한계가 있다. string→object Blackboard에 값형을 계속 넣으면 boxing 할당이 생긴다. memory composite가 terminal 뒤 인덱스만 되돌리고 child 상태를 정리하지 않으면 Wait 재진입이 즉시 끝날 수 있다. ReactiveSelector도 모든 자식이 Failure로 끝나는 경로의 이전 Running 정리를 별도 검토해야 한다. MoveTo의 고정 이동량은 도착 반경을 넘어 진동할 수 있다. 이 판단들은 정적 독해 추론이며 실행 재현은 하지 않았다.

Utility의 각 고려값을 0..1로 정규화하고 weight·곱셈·0 veto·보상식을 의도대로 정한다. 현재 행동 보너스·최소 유지 시간으로 근소한 점수 차이의 진동을 줄인다. 불가능 행동은 softmax 전 후보에서 제외한다. 점수가 0이라는 이유만으로 softmax 확률이 0이 되지 않는다. 빈 후보·NaN·온도·지수식 k=0 같은 경계도 검수 대상이다. 5~15Hz라는 결정 주기는 예시이며 반응 요구로 정한다.

### 카메라와 화면 좌표

캐릭터 이동 뒤 focus·deadzone·look-ahead·smoothing·화면 경계 순서로 갱신하고 shake는 별도 offset으로 더한다. 경계는 중심점만이 아니라 viewport 반폭·줌까지 고려한다. 순간이동/하드컷에서는 smoothing 상태를 재설정한다. `1-exp(-rate*dt)`의 고정 목표 지수 수렴과 `lerp(rate*dt)`의 근사는 동일하지 않다.

Cinemachine 2/3의 이름과 namespace를 섞지 않는다. Deoccluder의 시선 가림과 Decollider의 카메라 교차 방지를 구별한다. 원문 튜닝값은 승인된 프로젝트 구도·16:9 화면·배우 비율을 바꿀 근거가 아니다.

### 입력·UI 수명

버퍼는 시간 단위로 저장하고 수락 시 한 번 소비한다. 장치 능력과 현재 주 장치를 구별하고 작은 stick noise로 안내 아이콘이 계속 바뀌지 않도록 한다. 메뉴 스택 최상단이 입력·뒤로가기·포커스를 소유한다. 모달을 보여 주고 첫 버튼에 포커스를 주는 것만으로 뒷화면 접근을 완전히 막았다고 할 수 없다.

화면 크기·안전 영역·번역 길이·텍스트 확대·키보드/패드/터치의 실제 동선을 검수한다. CanvasScaler match 값 하나로 어떤 화면에서도 clipping이 없어진다는 보장은 없다. safe rect는 실제 좌표계와 부모 변환에 맞춰 변환하고 크기/방향 변화 때 갱신한다. 접근성 수치·규격 주장은 원문 출처와 대상 버전을 재확인한 뒤 제품 기준으로 채택한다.

hit-stop·트윈·UI 열기/닫기는 빠른 중첩 호출과 취소를 고려한다. timeScale을 무조건 1로 복원하면 pause/slow motion을 덮을 수 있으므로 이전 값과 소유권을 보존한다. 장식은 입력·정보·목표의 가독성을 방해하지 않는 범위에서 적용한다.

### 성능 측정

대상 기기·해상도·빌드·장면·부하·워밍업과 측정 구간을 먼저 고정한다. CPU/GPU·메모리·로딩 병목을 나누고 한 변경 뒤 같은 조건을 재측정한다. CPU와 GPU는 파이프라인으로 겹치므로 시간 값을 항상 단순 합산하지 않는다. draw call 감소가 CPU에는 무의미하다는 원문 보충 설명은 과도하다. CPU 제출 비용이 병목이면 도움이 될 수 있다.

pool은 획득·초기화·반납·최대치·초과 정책을 가진다. draw call, 투명 오버드로, 그림자, 텍스처, 해상도, 런타임 할당을 병목에 맞춰 다룬다. DPR 2는 같은 CSS 크기에서 1의 네 배 픽셀이다. 해상도 저하는 GPU fill 병목에는 도움이 될 수 있으나 CPU 시뮬레이션 개선을 보장하지 않는다. 평균 FPS와 에디터 화면만으로 모바일 품질을 확정하지 않는다.

## 9. 적용 작업의 검수·인계 양식

적용이 승인되면 `대상/고정 버전 → 원본 보존 → 최소 재현/기대 → 좁은 후보 변경 → 관련 정적 검사 → Editor → 대상 빌드/기기` 순서로 진행한다. 메시·형태 변경은 별도 실제 Guide와 보존 경계를 먼저 만든다. 이 교육 작업으로 그 단계를 실행한 것은 아니다.
