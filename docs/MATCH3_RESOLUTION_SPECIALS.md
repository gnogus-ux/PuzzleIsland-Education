# 매치3 · 해결 루프, 특수 조각과 장애물

[시작점](MATCH3_WORKFLOW.md) · [보드·입력](MATCH3_BOARD_INPUT.md). 이 문서는 학습 원리와 보완 설계다. 실제 특수/이벤트 순서는 적용할 프로젝트의 승인 계약을 따른다. [프로젝트 기준 안내](PROJECT_REFERENCE_GUIDE.md)를 먼저 읽는다.

## 먼저 매치 규칙을 구분한다

| 모양 | 가로·세로 직선 3 이상 | 같은 종류 연결 덩어리 3 이상 |
|---|---|---|
| `AAA` | 3칸 | 3칸 |
| 2+1의 작은 ㄱ | 직선3 없음 | 3칸 |
| 가로3+세로3이 한 칸에서 교차 | 검출 run 2개, 고유 제거5칸 | 연결 덩어리5칸 |
| 대각선으로만 3개 | 없음 | 상하좌우 연결이면 없음 |
| 떨어진 같은 색 3개 그룹 두 개 | 서로 다른 그룹 | 서로 다른 그룹 |

Winterbolt의 flood fill은 두 번째 규칙이다. 나머지 자료의 직선 run 검사 대신 넣으면 게임 규칙이 달라진다. 같은 색 ‘총수’를 세는 것도 연결 그룹 검사가 아니다.

직선 검출에서는 각 행을 왼쪽에서 오른쪽, 각 열을 아래에서 위로 훑는다. 종류가 바뀌거나 비활성/빈칸을 만나면 현재 run을 닫는다. 반복문 끝에 남은 run도 닫아야 우측·상단 끝 매치를 놓치지 않는다.

```text
각 행/열에 대해:
  run 시작과 길이를 유지
  같은 종류의 연속 유효 조각이면 길이 증가
  끊기면 길이>=3인 run을 기록하고 새 run 시작
  끝에서도 마지막 run 기록
모든 run으로 고유 제거 좌표 집합 생성
연결된 run과 교차점을 묶어 패턴별 그룹 구성
```

길이3 슬라이딩 창을 HashSet에 넣는 git-amend 방식도 긴 직선의 고유 좌표를 얻는다. 그러나 HashSet 하나만 남기면 4/5/T/L의 방향·중심·원인을 잃는다. 특수 생성이 필요하면 run/그룹 메타데이터를 따로 보존한다.

## ‘검출’과 ‘적용’을 분리한다

보드를 훑으면서 즉시 Destroy하고 점수·폭탄을 만들면 뒤쪽 검사가 이미 변한 판을 읽는다. 먼저 안정된 한 상태에서 검출하고, 생성/보존/타격/피해를 계획한 뒤 한 번 적용한다.

| 결과 데이터 예 | 필요한 이유 |
|---|---|
| run의 시작·길이·방향·종류 | 직선4/5와 교차 패턴 분류 |
| 그룹 ID와 고유 셀 | 떨어진 동일 색 그룹을 섞지 않기 |
| 원인 명령과 조각 ID | 생성 앵커를 교환한 조각에 연결 |
| 보존/변환 셀 | 새 특수가 같은 제거에서 사라지지 않기 |
| 이벤트 ID·원인 이벤트 ID | 특수의 재진입·중복 피해·중복 보상 방지 |
| 제거·피해·변환·낙하·보충 결과 | 화면과 QA가 판정을 다시 계산하지 않기 |

Taft에서는 전역 `currentMatches.Count`가 4/7 또는 5/8인지로 패턴을 추측하는 편이 있다. 서로 떨어진 그룹의 합이나 긴 직선을 구별하지 못한다. 후속 `MatchType {type,color}`는 생성 색 보존을 개선하지만 연결 그룹 문제 전체를 해결하지 않는다.

점수도 고유 제거 수·run 길이 합·그룹 크기 중 무엇을 쓰는지 정한다. Catlike는 검출한 각 run의 길이를 합하고 run마다 multiplier가 증가한다. 교차점을 제거 한 번만 해도 점수에는 두 run이 반영된다. 이를 ‘교차점 중복 점수 오류’로 단정하려면 먼저 그 게임의 점수 정책이 필요하다.

## 한 명이 해결을 끝까지 소유한다

```text
수락된 명령 1개
  시험 교환/승인 특수 명령 확정
  while 해결할 매치 또는 예약 효과가 있음:
    그룹·특수 생성·보존 셀 결정
    효과 큐를 방문/이벤트 가드로 처리
    피해와 실제 제거를 한 번 적용
    점수·목표의 논리 결과 누적
    구간별 압축·보충
    연쇄 결과 프레임 기록
    새 매치 검사
  안정판의 목표/종료/가능 수 판정
  전체 결과를 화면에 전달
  화면 완료 후 세션이 입력 또는 결과 화면으로 전환
```

매 조각 `Update`에서 검사 coroutine을 시작하고, 각 제거 함수가 다시 낙하/리필을 시작하면 여러 루프가 같은 배열을 건드린다. Taft P34·50의 지연·`yield break` 정정은 이 증상을 줄이는 과정을 보여준다. 단순히 0.5초를 더 기다렸다고 소유권과 원자성이 확보되는 것은 아니다.

coroutine은 기다리는 지점에서 제어를 돌려주는 순차 흐름이다. 같은 주 스레드에서 실행되어도 여러 coroutine 사이에 상태가 바뀌는 재진입 문제는 생긴다. `FindAllMatches()`가 coroutine을 시작하고 바로 반환한다면 그 다음 줄에서 읽은 플래그는 새 검사 결과가 아닐 수 있다. 순수 동기 검출 또는 완료를 기다리는 명시 계약이 필요하다.

승리/패배·일시정지와 해결 단계도 분리한다. `FillBoardCo` 마지막 줄에서 무조건 `move`를 넣으면 승리/패배/pause를 덮을 수 있다. Pause에서 돌아올 때도 이전 상태를 보존해야 한다. ‘입력 잠금’과 ‘화면 애니메이션/시간 정지’는 별도 정책이다.

## 낙하와 보충

빈칸마다 위를 다시 탐색하는 방식은 직관적이지만 같은 열을 반복 탐색한다. 연속 중력 구간마다 아래쪽 쓰기 위치를 두고 생존 조각을 한 번 훑으면 순서를 보존하며 압축할 수 있다.

1. 구간의 아래부터 위로 생존 조각을 읽는다.
2. 다음 쓰기 위치로 이동시키고 `id/from/to`를 기록한다.
3. 남은 위쪽 칸에 새 조각을 정해진 순서로 만든다.
4. 생성점은 실제 구간 위쪽을 사용한다. 화면 바깥 offset을 논리 좌표에 섞지 않는다.
5. 보충 후 다시 매치를 검사한다.

마스크 구멍은 열을 여러 구간으로 나눌 수 있다. 고체 장애물도 경계인지, 위에서 통과 가능한지 정책을 먼저 정한다. 젤리·잠금 바닥은 조각 점유와 다른 층이다. 구멍을 ‘당장 비어 있는 칸’으로 처리해 채우면 안 된다.

화면 이동 시간은 거리/속도 또는 미리 정한 easing으로 계산할 수 있다. 여러 조각이 동시에 움직이면 가장 늦은 실제 완료까지 Busy를 유지한다. 고정 `WaitForSeconds(0.1)` 뒤 다음 단계로 가면서 tween은 0.5초인 코드는 논리/표현 완료가 어긋난다. 씬 종료·취소·화면 복구도 별도 경로로 처리한다.

## 특수 생성과 연쇄

특수 생성에는 패턴 우선순위, 생성 위치, 원래 색/방향, 보존할 조각, 자연 연쇄에서 생성할지 여부를 명시한다. Taft는 후반에 자연 연쇄에서는 특수를 만들지 않는 정책을 말한다. 이는 그 강좌의 선택이며 현재 프로젝트 정책을 바꾸는 근거가 아니다.

폭탄에서 다른 폭탄을 찾을 때 서로를 재귀 호출하면 순환할 수 있다. 적용 전에 조각 ID 또는 이벤트 인스턴스를 방문 집합에 기록하고, 효과 큐에서 각 원인을 한 번 처리한다. 타격 범위 집합과 실제 제거 집합, 장애물 피해를 구별한다. 같은 셀을 두 효과가 타격할 때 HP가 한 번 줄지 두 번 줄지는 승인 정책에 따른다.

LINQ `Union`은 원래 리스트를 수정하는 명령이 아니다. 결과를 받지 않으면 합쳐지지 않는다. 같은 리스트를 도는 동안 원소를 하나씩 지워 조건이 바뀌는 것과, 먼저 검출 집합을 확정하고 마지막에 Clear하는 것도 다르다. Taft P21의 6→5→4 생성 문제와 P35의 Union 호출은 이 차이를 확인하는 자료다.

## 장애물 추가 시 함께 확인할 경로

| 경로 | 질문 |
|---|---|
| 초기 생성 | 차단 셀에 조각이 생성되는가? |
| 입력 | 출발·목적 잠금과 특수 예외가 일치하는가? |
| 매치 | 장애물을 넘어 run을 잇는가? 다른 층의 바닥 목표인가? |
| 효과 | 행/열/사방/대각 범위, 구멍 통과, 여러 HP 피해 정책은? |
| 제거 | 실제 조각 제거와 바닥/장애물 목표 완료는 언제인가? |
| 낙하·리필 | 구간 경계를 지키는가? 생성점은 맞는가? |
| 힌트·교착 | 잠긴 교환·빈칸 교환을 합법으로 세는가? |
| 셔플/재생성 | 고정 장애물과 종류·특수·ID 보존 정책은? |
| 저장/재개 | 장애물 HP·턴 상태를 지원하는가, 안정판만 재개하는가? |

Taft Concrete의 행/열 폭탄 코드는 처음에 전체 2중 루프와 다른 인덱스 검사/피해를 사용했다. P54에서 정리하지만 열을 순회하며 `i < width`가 남은 화면도 확인했다. 열의 세로 범위는 height다. 정사각형에서만 시험하면 잔여 오류를 못 찾는다.

Slime의 증식도 턴당 한 개, 원본 슬라임당 한 개, 피해를 받으면 억제 중 어떤 정책인지 명시한다. 이웃 배열을 읽기 **전에** bounds를 확인하고, 모든 후보를 먼저 모아 선택한다. 전체판 무작위 위치를 200번 뽑는 것은 균일한 유효 후보 선택이나 반드시 한 개 성공을 보장하지 않는다. 성공 후 반복을 멈추지 않으면 한 턴 여러 증식이 가능하다.

## 집중 검증 사례

| 사례 | 봐야 할 결과 |
|---|---|
| 행 끝/열 끝 3·4·5 | 마지막 run flush와 방향 |
| T/L과 서로 떨어진 그룹 | 고유 제거 수, 그룹별 생성, 점수 정책 |
| 색 폭탄+일반/특수 | 보존·변환·발동 순서와 이벤트 중복 |
| 서로 타격하는 행/열 폭탄 | 큐 종료, 같은 인스턴스 재발동 없음 |
| 마스크로 끊긴 한 열 | 구간 밖 조각/생성점 침범 없음 |
| 다중 HP 장애물에 여러 인접 제거 | 파동/이벤트당 피해 정책대로 집계 |
| 연쇄 중 입력·pause·씬 종료 | 해결 소유자 하나, 종료 상태 보존 |
| 한 종류뿐인 잘못된 레벨 | 무제한 생성/연쇄 대신 명시 실패 |

교육 중 이 사례를 게임에서 재현하거나 기존 특수 시스템을 수정하지 않았다. 구현 검수에서는 예상 판·난수·고유 ID와 실제 결과를 대조한다.
