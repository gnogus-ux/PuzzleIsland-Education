# UV·재질·Texture Set·아틀라스와 출력 인계

[UV 시작점](UV_WORKFLOW.md) · [밀도·패킹](UV_TEXEL_DENSITY_PACKING.md) · [Painter 제작 흐름](PAINTER_CHARACTER_WORKFLOW.md) · [Painter → Blender 채널](PAINTER_TO_BLENDER.md)

UV와 이미지, 재질, Texture Set은 서로 대응하지만 같은 데이터는 아니다. 주요 근거는 [Josh/BlenderBros](https://www.youtube.com/watch?v=j9uEqZxJMbY), [Dikko](https://www.youtube.com/watch?v=ZyRtd8iYBOg), [Huge Menace](https://www.youtube.com/watch?v=sR1sAWWT2x8)다. Painter·Unity에 대한 인수 항목은 기존 교육자료와 제작 원리를 보강한 체크리스트이며 이 다섯 영상이 실제 엔진 이식까지 시연했다는 뜻은 아니다.

## 먼저 용어를 분리한다

| 용어 | 실제 의미 | 흔한 혼동 |
|---|---|---|
| UV 맵 | 메시의 면 코너별 좌표 집합, 하나의 메시가 여러 맵을 가질 수 있음 | 재질을 추가하면 UV 맵이 자동으로 별도 생성된다고 생각함 |
| 재질 슬롯/할당 | 어떤 면이 어떤 재질을 사용하는지와 그 셰이딩 설정 | 같은 재질이면 모든 면이 같은 이미지 부분을 읽는다고 생각함 |
| 이미지 | 색·노멀·거칠기 등을 저장한 파일과 채널 | 파일명만 보고 RGB/알파 의미를 확정함 |
| Texture Set | Painter에서 재질 할당 등을 기준으로 구성되는 작업/출력 단위 | 모든 오브젝트가 자동으로 하나의 세트가 된다고 생각함 |
| UDIM 타일 | 하나의 UV 타일 집합에 속하는 1001, 1002 등의 이미지 영역 | 새 재질 세트 또는 별도 UV 맵과 동일시함 |
| 아틀라스 | 여러 부품/자산의 이미지 영역을 한 이미지 구성으로 공유 | 오브젝트 Join만 하면 재질/드로 콜까지 합쳐진다고 생각함 |

Josh 영상의 “각 재질의 UV”는 별도 이미지 예산을 받는 면 그룹으로 읽는다. 재질마다 UV 레이어가 자동 생성되는 기능을 뜻하지 않는다. 여러 오브젝트를 Join해도 재질 슬롯과 면 할당은 남을 수 있고 셰이더·이미지가 자동으로 아틀라스로 구워지지 않는다.

## 단일 타일·여러 세트·UDIM을 고르는 조건

| 구성 | 먼저 고려할 상황 | 반드시 확인할 비용 |
|---|---|---|
| 0~1 고유 한 세트 | 예산이 제한되고 묶어서 출력·관리하기 쉬운 자산 | 얼굴과 큰 몸 표면이 같은 타일을 나누는 밀도 |
| 여러 재질/세트 | 눈·피부·의상 셰이더나 출력 규약, 수정 주기가 다른 경우 | 세트별 해상도×채널, 렌더 패스·메모리·전환 비용 |
| UDIM | 도구 체계가 지원하며 가까운 촬영에 큰 고유 면적이 필요한 경우 | 타일 저장/누락, 출력·베이크·게임 셰이더 지원과 예산 |
| 여러 자산 아틀라스 | 동시에 쓰이는 호환 재질의 소품들이 빈 공간을 공유할 때 | 한 부분 변경에 따른 재출력, 로딩/스트리밍 결합, mip 간섭 |
| 의도된 UV 겹침 | 대칭·반복 표면의 동일 무늬 재사용 | 비대칭 표현 상실, 투영·노멀/AO 베이크 충돌 |

Dikko는 2048² UDIM 1001~1004의 캐릭터 예와 타일별 저장을 보여주지만 게임·초보 작업에는 단일 0~1도 설명한다. Josh의 문 부품별 4096²는 가까운 렌더 예다. 이를 모바일의 필수 이미지 수·해상도로 삼지 않는다. “게임에는 UDIM이 절대 불가능하다” 또는 “재질은 반드시 두 개 이하” 같은 규칙도 만들지 않는다. 실제 고정 엔진/셰이더와 예산으로 판단한다.

참고로 압축하지 않은 4096² RGBA8 한 장은 64MiB이며 전체 mip 체인은 대략 4/3배다. 이는 이론적 데이터 예시다. 실제 런타임 압축·채널 수·플랫폼 포맷·스트리밍·동시 상주량에 따라 달라지므로 측정치로 보고하지 않는다. 4K 여러 장을 사용한 영상 결과가 곧 모바일 예산 통과의 근거는 아니다.

## Painter에 넘길 고정 정보

텍스처를 별도 담당이 만들어도 UV 계약이 필요하다. 메시를 내보낸 후 UV나 토폴로지가 바뀌면 기존 투영·베이크·페인팅과의 대응이 달라질 수 있다. 변경 후보와 기존 텍스처를 구분해 전달하고 재베이크/재투영 필요성을 기록한다.

| 인계 필드 | 적을 내용 |
|---|---|
| 메시 | 파일 버전, 오브젝트/부분 이름, 단위·크기, 삼각화/법선 기준 |
| UV | 맵 이름·사용 채널, 타일 목록, 레이아웃, 허용 겹침 쌍, 방향 제한 |
| 재질 | 슬롯 이름, 할당된 부위, 예상 Texture Set, 셰이더 차이 |
| 이미지 | 세트별 W×H·비트 깊이·색공간, RGB/알파 의미, 파일명 규칙 |
| 베이크 | high/low 대응, cage/거리, 노멀 규약, 겹침 분리 방식, padding |
| 검수 | 동일 조건 전후, 가시부 체크, 실제 게임 카메라 크기, 남은 결함 |

임포트 후에는 실제 생성된 Texture Set 수와 이름을 대조한다. 예상과 다르면 재질 할당/내보내기 옵션부터 확인한다. 고유 페인트가 필요한 면이 포개져 있으면 두 곳에 같은 획이 생길 수 있다. 겹침은 출력용 재사용 정책과 베이크용 배치 정책을 구분해 시험한다. 베이크 때 한쪽을 옮기는 기법을 모든 도구에서 자동 안전하다고 가정하지 않는다.

눈의 별도 텍스처에는 홍채 중심·경계·UV 방향, 좌우 공유 여부, 최종 눈 메시 버전을 포함한다. 파일명만 `Eye`로 정하는 것은 충분한 계약이 아니다. 피부와 같은 이미지에 배치하더라도 눈의 다른 거칠기·노멀·투명/굴절 요구가 사라지지는 않는다.

## Blender와 게임에 받을 때

[Painter → Blender](PAINTER_TO_BLENDER.md)의 RGB/알파·Glossiness 반전·Normal 규약을 먼저 읽는다. UV가 맞아도 채널 연결이 틀리면 피부와 눈의 재질이 달라진다. 텍스처 파일명이 Metallic이라고 알파가 Roughness라는 뜻은 아니다. 데이터 맵을 색 이미지와 같은 방식으로 읽거나 노멀 Y를 중복 반전하지 않는다.

Unity 등의 게임 인계에는 **베이스컬러용 UV와 라이트맵용 UV의 목적**을 구별한다. 고유 라이트맵 영역에서는 겹침과 간격 요구가 달라질 수 있다. Blender의 UV 맵 순서가 내보내기 후 의도한 엔진 채널과 같다고 추정하지 않고 실제 임포트 데이터/머티리얼에서 확인한다. 이번에는 현행 Unity 공식 문서·프로젝트 임포트 UI를 새로 대조하지 않았으므로 메뉴 위치·자동 생성 설정을 확정하지 않았다.

아틀라스는 호환 셰이더/머티리얼을 공유할 기회를 줄 수 있지만 드로 콜 감소를 보장하지 않는다. 메시·재질 슬롯·렌더 패스·투명도·배칭·그림자 조건까지 프로파일러에서 확인해야 한다. 모듈형 섬 소품의 다른 크기와 반복 개수를 고려하며, UV 예제를 이유로 이미 승인된 모듈 크기나 구조를 바꾸지 않는다. 타일 재질/트림시트의 완성 제작법은 이번 5강의 범위 밖이다.

## 인수 결과를 쓰는 방식

`파일 생성`, `열기 확인`, `체커 검사`, `베이크`, `재질 연결`, `게임 카메라`, `기기 측정`을 별도 항목으로 적는다. 수행한 항목만 PASS, 남은 결함은 PARTIAL, 하지 않은 검사는 NOT_RUN으로 둔다. 타일 이미지를 각각 저장했는지, 외부 경로가 깨지지 않는지도 확인한다. .blend 저장 성공만으로 모든 이미지 파일이 저장/포함되었다고 보고하지 않는다.

이번 교육에서는 실제 메시 내보내기·Painter 프로젝트 생성·베이크·텍스처 제작·Blender 연결·Unity/Android 검증을 수행하지 않았다. 앱 연결 테스트는 수행하지 않았다.
